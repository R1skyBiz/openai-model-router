# Source gap plan v1 — Segment 2.5

The current baseline is **35 conservative work-product groups**, covering 44 accepted/repaired cases. Reaching 60 requires **25 additional qualifying groups**; reaching 200 requires 165. This plan requests **30 additions**, allowing five groups of headroom. These are collection targets, not discovered records, accepted cases or evidence that the milestone is achievable from currently available sources.

## Counting and priority

Use one original investigation or separately commissioned deliverable as the collection unit. Preserve revisions, follow-up measurements, alternative calculations, tool steps and final decisions within that parent. A new chat, output format, test function or model answer does not establish a new work product. Split only when original records establish independently useful deliverables with separate acceptance criteria. Apply one primary domain per group for this plan; retain secondary tags without adding counts. This domain view does not rewrite stored case families.

The counts below are a conservative domain assignment from the [owner packet](owner-review-packet-v1.md): the siphon explanation is one pumps/fluid-systems group; the tray-volume calculation is one engineering-calculation group (stored family remains `math`). Neither establishes a crop-system or controlled-environment-agriculture investigation. The other **33 groups are software/writing work outside these physical-domain and executed-tool priorities**. Software cost/percentile arithmetic is not counted as physical engineering. Current counts below sum to two; two plus 33 reconciles to 35. Both physical-domain groups overlap earlier pilot controls and await original-record revalidation.

## Acquisition and acceptance sequence

1. Request owner-authorized original records in the priority order above, using the [private intake guide](private-source-intake-guide.md). Do not mine unrelated private locations. Collect the original request, relevant user-provided context, dates/order, attachments, constraints, task boundary, observed outcome and evidence supporting acceptance. An unresolved or failed historical outcome is eligible evidence if its task and fair grading can be established; assistant prose alone is not gold truth.
2. Build a private candidate ledger recording opaque parent/work-product IDs, primary category, evidence gaps, privacy review, grading feasibility and proposed disposition. Compare against all 35 groups and pilot controls, including cross-conversation continuations. Collect additional records where duplicates or insufficient evidence reduce yield; never relax requirements to fill a row.
3. Prioritize the 28 physical-domain additions that can support bounded, self-contained grading. Preserve the original consequence and defer unsafe/incomplete or operational tasks; rewriting a real execution task into prose is a changed task, not its completed historical replay.
4. Review the two tool candidates separately for executable acceptance. Existing seven deferrals are possible recovery leads, not guaranteed new groups or automatic credits. Their relationship to existing assignments and prior pilot work must be adjudicated first.
5. Freeze only an owner-reviewed future corpus version and recalculate distinct groups after deduplication. Keep originals, rejected/deferred evidence and mapping decisions private. No intake or freeze is performed in Segment 2.5.

## Milestone arithmetic and unresolved dependencies

Under the existing accounting contract, **35 + 25 = 60**; accepting all 30 proposed additions would yield **65**. If the two tool additions remain unsupported but all 28 physical-domain additions qualify, the result is **63**. If the milestone also excludes the three pilot-overlapping parents, **32 + 28 = 60** without tool credits. These are conditional arithmetic scenarios, not forecasts. Broader merging of repository functions can lower the baseline further; the required number is always `max(0, 60 - adjudicated_existing_groups)`.

Remaining blockers are authorized originals, complete engineering context, privacy-preserving sanitization, broader work-product adjudication, human rubric/answer anchors and executable tool support. Automated review is not independent human agreement. This plan leaves accepted/repaired, rejected and deferred statuses unchanged, adds no cases, and leaves the canary disabled. Paid calls and remote push remain outside scope.
